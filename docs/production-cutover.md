# 新HP公開切り替え・旧HPへの切り戻し手順

作成：2026-10-20。これは実施前の手順書。公開操作・DNS変更・旧HP移動は未実施。

## 対象と維持するもの

- 公開ドメイン：`https://mitamurafarm.com/`
- 公開フォルダー：`/home/mitamurafarm/mitamurafarm.com/public_html`
- 本番アプリ：`/home/mitamurafarm/apps/mitamura-production`
- プレビュー：公開フォルダー内の `preview.mitamurafarm.com` と `/home/mitamurafarm/apps/mitamura-preview`。切替・復旧とも変更しない。
- 旧HP保存版：プレビューの管理メニュー「旧HP保存版」。原本は非公開アーカイブに保持。
- 本番DB、APP_KEY、管理者、SMTP暗号化ファイルは保持。プレビューのDBやテスト受付を本番へ移さない。
- メールアカウント・MX・SPF・DKIM・DMARC、Googleバックアップ連携は変更しない。ドメイン/DNS切替方式ではなく、同じサーバー内の配信ファイル切替とする。

## 1. 公開前の停止条件

次の項目が残っていれば公開切替を行わない。準備用ファイルの配置と公開は区別する。

- 販売主体等の保留情報、商品/在庫、手数料案内、発送・返品条件の最終確認が未完了。
- 制作プレビュー/実注文不可等の公開用文言への切替が未完了。
- 公開予定リビジョンが未確定、またはプレビュー確認版と本番候補が不一致。
- 本番管理者のHTTPログイン、実受付・農園通知・受付返信の確認手順が未準備。
- 最終バックアップや切り戻し用ファイル一覧がない。
- 本人の公開承認がない。

Squareの審査待ちは初回公開の停止条件にしない。初回の支払いは銀行振込・郵便振替・代引きで、カードは準備中・利用不可と案内する。

## 2. 承認前に行う準備

1. 公開候補のGitリビジョンを固定し、テスト・プレビュー確認を完了する。
2. `stage-production-release.sh` で候補を本番非公開releasesへ配置。既存currentとWeb公開先は変更しない。未適用migrationがあれば中止して別途検討する。
3. `check-launch-readiness.php` を環境変数を引き継がないCLIで実行し、管理者・SMTP復号・権限・受付停止・メールlog・検索除外・DB状態を確認。秘密値は表示しない。
4. 本番候補で商品マスタ、メール本文、返信先、公開用文言を照合する。プレビューで商品を変更していても、本番へ反映済みと推測しない。
5. 旧URL対応表を `seo-launch.md` と照合し、保存版の旧HTMLからリンク先を確かめる。旧画像・PDFを無差別にトップへ転送しない。
6. 変更対象一覧を作る。公開フォルダーの相対パスごとに「既存の有無・旧ハッシュ・新ハッシュ・退避先」を残す。`.htaccess`、入口PHP、CSS/JS/画像、旧ページ/CGIの扱いを含める。

事前チェックの成功は、公開承認やApache設定の実動作保証を意味しない。

## 3. 公開承認後、切替直前

1. 公開予定時間と切り戻しの判断基準を本人へ伝える。
2. 旧HPをもう一度バックアップする。プレビュー用ディレクトリを除外し、`.htaccess`・`.user.ini`・CGI等を含める。圧縮整合性とSHA256を確認し、サーバー非公開領域とPCへ保存する。
3. 本番DB/.env/SMTP設定を新規バックアップし、Drive転送・照合を確認する。切替前currentの参照先も記録する。
4. 公開フォルダーの容量・所有権・PHP設定を確認する。既存 `.htaccess` と `.user.ini` のPHP/キャッシュ関連設定を保全し、Laravelの設定で無条件に上書きしない。
5. ファイルは公開フォルダー外へ事前配置・検証する。`.env`・vendor・storage・バックアップを公開フォルダーへコピーしない。

## 4. 切替時に必要な操作（未実施）

- 入口PHPは確認済みの本番リリース絶対パスに固定する。単なるcurrentリンク切替だけでPHPのキャッシュ更新が済むとは扱わない。
- `DirectoryIndex` を明示し、旧 `index.htm` が新しい入口より優先されないようにする。
- 旧HTML/CGIは変更対象一覧に沿って非公開退避し、公開された旧注文フォームが残らないようにする。ファイルを削除する代わりに退避し、元の相対パスを保持する。
- 旧URLの転送は公開ホストだけに限定する。親フォルダーの `.htaccess` がプレビューへ影響し得るため、プレビューや保存版への転送・認証破壊がないことを確認する。
- 旧フォーム送信先は新HPの受付へ転送して再送信させず、利用終了の案内にする。旧HTML/画像へのアクセスとフォームPOSTは分ける。
- 本番だけ `APP_URL=https://mitamurafarm.com`、`PREVIEW_REQUIRE_LOGIN=false`、`INQUIRIES_ENABLED=true`、`MAIL_MAILER=smtp` を設定。実客へ送る段階で本番の宛先制限を解除する。プレビューの制限は維持する。
- `SEO_INDEXABLE=true` は公開確認と同時に本番だけ有効にする。管理画面・保存版の検索除外は維持する。
- 本番用に独立したセッションCookie名を維持する。プレビューとログイン状態を共有させない。
- configキャッシュを作り直す。平文SMTPパスワードがキャッシュに含まれないことを確認する。
- 新規ファイルは一時名で準備してから入口・設定を切り替える。複数ファイルの切替を完全に原子的と説明しない。

## 5. 切替直後の確認

1. 未ログインでトップが200、HTTPS・www統一・画像・CSS/JS・スマホ表示が正常。
2. canonical・OGP・sitemap・robotsとHTTPヘッダーを確認。公開ページにnoindexが残らず、管理画面・プレビューに検索許可が出ない。
3. 本番管理者でログインし、商品/受付画面を確認する。プレビューも別セッションで開けることを確認。
4. 本人管理のメール宛てに「公開確認・実注文ではない」受付を1件送り、本番保存・農園通知・受付メール・返信先・二重登録防止を確認。受付番号を内部記録し、実注文として処理しない。
5. 旧URLの転送と404、旧フォーム停止、旧HP保存版の認証・画像・主要ページを確認する。
6. エラーがあれば受付を停止して切り戻す。正常なら公開リビジョン・バックアップ・確認結果を重要設定一覧へ記録する。

## 6. 旧HPへ切り戻す場合

判断例：トップの継続的な5xx、フォーム保存不能、管理者ログイン不能、公開範囲や秘密ファイル露出の問題、短時間で安全に解決できない配信異常。メールだけの障害でも受付保存の有無を調べ、まず受付を止めて本人に状況を伝える。

1. 本番の新規受付を停止し、設定キャッシュを更新する。公開後に受け付けたデータとログをバックアップする。
2. 変更対象一覧から今回追加した公開ファイルを特定し、非公開の切り戻し用退避先へ移す。公開フォルダーを丸ごと削除・移動しない。プレビュー・保存版・他サービスのファイルを触らない。
3. 切替直前に退避した旧ファイル・元の `.htaccess` を元の相対パスへ戻す。`.user.ini` を変更していた場合も記録した原本から戻す。新しいindex.phpを残して旧index.htmの表示を妨げない。
4. 本番currentを切替前の参照先へ戻す。必要なキャッシュ更新後に、旧トップ・画像・主要ページ・プレビュー・保存版をHTTP確認する。
5. **DBを切替前へ戻さない。** 公開後の受付を消さず、新HPのDB・APP_KEY・暗号化SMTP設定を維持する。データ障害時のDB復元は別の判断と手順で行う。
6. 受付済み問い合わせの通知状態を確認し、担当者が必要な案内を行う。外部メールを自動再送しない。
7. 時刻・理由・退避/復元ファイル・受付対応・再公開の条件を記録する。

## 本番総合確認を行う際の条件（未実施）

- 公開前に本番HTTPログイン・受付を試すには、HTTPSと管理者認証で保護された本番専用の確認入口が必要。現在のプレビューへ本番DBをつなぎ替えて代用しない。
- 現在の本番候補はWeb未接続・受付停止・メールlogのため、画面生成やSMTP単独テストの成功を総合確認と呼ばない。
- 確認入口は本番だけのセッションCookieを用い、検索除外・農園Gmailへの送信制限を維持する。準備前に受付停止や宛先制限を解除しない。
- 本人が本番の管理者情報でログインし、指定テスト商品を送信する。本文に「公開前テスト・実注文ではない」を明記し、農園Gmailを返信先に使う。
- 保存件数・商品/数量・金額目安・受付番号・管理画面・通知2通・返信先・再送防止を確認する。自動注文確定や実請求を行わない。
- 完了後は受付停止・メールlogを復帰して確認入口を閉じる。テスト受付は識別して保持し、実注文として扱わない。削除や実メール再送は別途判断する。

本番確認用フォルダーcheck.mitamurafarm.comは、プレビューと同様に旧HPバックアップ・公開切替時の退避/復旧対象から除外する。確認入口は必要時のみ有効にし、終了後は非公開フラグで停止する。

確認入口の停止方法：本番非公開領域のhttp-check-enabledフラグを無効化すると入口PHPは503を返し、以後の新規リクエストを受け付けない。サブドメインの公開ファイルを削除して停止する必要はない。通常本番の受付停止・メールlog・旧HP公開は維持する。確認中に開始済みのリクエストまで取り消す仕組みではない。
